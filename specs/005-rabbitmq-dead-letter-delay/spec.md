# Feature Specification: RabbitMQ 死信与延迟队列拓扑

**Feature Branch**: `[005-rabbitmq-dead-letter-delay]`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "`com.dhl.base.config.mq.visualize.GenerateClearanceStatusMqConfiguration#broadcastWriteOffQueue` 建议增加这种死信队列以及延迟队列的支持"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 识别死信转发关系 (Priority: P1)

开发人员查看 RabbitMQ 拓扑时，可以识别哪些普通队列配置了死信交换机，并看到源队列、死信交换机、死信路由键以及能够静态确定的目标死信队列。这样无需逐个追踪队列参数、交换机和绑定声明，就能理解消息失败或过期后的流向。

**Why this priority**: 死信关系是本功能的基础；若不能把队列参数与现有交换机、绑定和目标队列关联起来，单独展示一个普通队列名称无法帮助排查消息流向。

**Independent Test**: 在只读样例项目中声明一个带死信交换机和死信路由键的源队列，再声明目标交换机、绑定和死信队列；打开 MQ Navigator 即可独立验证完整死信路径、属性和各节点源码定位。

**Acceptance Scenarios**:

1. **Given** 一个队列声明了静态死信交换机和静态死信路由键，且项目内存在匹配绑定与目标队列，**When** 用户查看该队列，**Then** 系统展示从源队列到死信交换机再到目标死信队列的完整关系。
2. **Given** 一个队列只声明了静态死信交换机，未声明专用死信路由键，**When** 用户查看该队列，**Then** 系统说明消息沿用原路由键，并仅在现有绑定足以确定目标时展示精确目标队列。
3. **Given** 一个队列声明了死信交换机，但项目内缺少匹配交换机、绑定或目标队列，**When** 用户查看该队列，**Then** 系统仍展示已解析的死信参数，并明确提示目标在当前项目中无法确定。
4. **Given** 死信交换机或路由键来自可静态解析的常量、局部变量或参数集合，**When** 系统扫描项目，**Then** 展示结果与源码中的实际值一致。

---

### User Story 2 - 识别 TTL 延迟队列 (Priority: P1)

开发人员查看同时配置队列存活时间和死信交换机的 RabbitMQ 队列时，可以明确识别这是基于消息过期转发的延迟队列，并看到延迟时长及延迟结束后的消息去向。

**Why this priority**: 用户指定的 `broadcastWriteOffQueue` 同时使用队列存活时间和死信交换机；只有组合展示延迟时长与后续路由，才能准确表达该队列的实际用途。

**Independent Test**: 在只读样例项目中声明一个静态存活时间、死信交换机和可选死信路由键的队列，验证该队列被标识为延迟队列、延迟时长正确、后续死信路径可追踪，且不依赖真实 RabbitMQ。

**Acceptance Scenarios**:

1. **Given** 一个队列同时声明了静态非负存活时间和静态死信交换机，**When** 用户查看拓扑，**Then** 系统将其标识为延迟队列，并展示延迟时长和过期后的转发关系。
2. **Given** 一个队列只声明存活时间而没有死信交换机，**When** 用户查看拓扑，**Then** 系统展示存活时间属性，但不将其描述为具有可追踪后续路径的延迟队列。
3. **Given** 一个队列只声明死信交换机而没有存活时间，**When** 用户查看拓扑，**Then** 系统将其作为死信来源队列展示，不将其标识为延迟队列。
4. **Given** 存活时间无法静态解析或不是有效的非负时长，**When** 用户查看该队列，**Then** 系统保留队列节点并提示延迟时长无法确定，不猜测具体数值。

---

### User Story 3 - 在现有侧边栏中追踪特殊队列 (Priority: P2)

开发人员可以继续使用现有模块分组、搜索、类型筛选、刷新、缓存恢复和双击导航来查找死信队列与延迟队列。特殊队列关系应作为现有 RabbitMQ 拓扑的补充，而不是形成第二套互相独立的浏览入口。

**Why this priority**: 识别结果必须融入已有使用路径，才能在大型多模块项目中快速定位，并避免破坏已完成的侧边栏、刷新和缓存能力。

**Independent Test**: 在包含普通队列、死信来源队列、目标死信队列和延迟队列的多模块样例项目中，分别执行搜索、筛选、刷新、重启后缓存恢复和双击导航，验证特殊队列属性及关系始终一致。

**Acceptance Scenarios**:

1. **Given** 死信来源、死信目标或延迟队列分布在不同模块，**When** 用户按模块展开拓扑，**Then** 每个声明保留所属模块，跨模块关系仍可查看和跳转。
2. **Given** 用户按队列名、交换机名、路由键或特殊队列类型搜索，**When** 搜索命中相关属性，**Then** 系统只展示符合当前搜索和消息系统筛选条件的相关结果。
3. **Given** 用户刷新项目或重新打开项目并恢复缓存，**When** 再次查看同一特殊队列，**Then** 类型、时长、死信参数、关系和源码位置与最近一次完整扫描结果一致。
4. **Given** 用户双击源队列、死信交换机、绑定或目标队列，**When** 对应源码仍有效，**Then** 系统跳转到该信息的实际声明位置。

### Edge Cases

- 参数集合除死信和存活时间外还包含 quorum 等无关队列参数，特殊队列识别不得受干扰。
- 同一死信参数通过连续单值设置或一次参数集合设置，识别结果必须一致。
- 参数集合在声明前经过条件分支、后续覆盖或无法静态追踪的修改，不得用某个分支值冒充唯一结果。
- `x-dead-letter-routing-key` 缺失时，需要区分“沿用原路由键”和“空字符串路由键”。
- `x-message-ttl` 为 `0` 时仍应保留真实值，不得当作缺失；负数、非数字或无法解析的值应显示诊断。
- 死信交换机存在但没有绑定，或者绑定存在但目标队列声明位于项目之外，系统不得虚构目标队列。
- 一个死信交换机通过多个绑定匹配多个目标队列时，必须保留全部静态匹配结果，不得任意选择一个。
- 源队列、交换机、绑定和目标队列跨模块或声明顺序相反时，关系结果不得变化。
- 同一队列重复声明时，不得因新增特殊属性而产生无法解释的重复关系。
- 死信关系形成环路时，只展示静态声明关系，不得递归展开导致界面卡死。
- 动态队列名、动态交换机名、动态路由键或动态存活时间必须保留可见节点和具体诊断。
- 普通 RabbitMQ、Kafka 和 RocketMQ 端点不得因本功能改变既有识别、匹配和导航结果。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 识别 RabbitMQ 队列声明中的死信交换机、可选死信路由键和队列存活时间，并将这些属性关联到对应队列声明。
- **FR-002**: 系统 MUST 支持从单个参数声明和参数集合声明中读取上述特殊队列属性，两种声明形式产生相同的用户可见结果。
- **FR-003**: 系统 MUST 解析可静态确定的字面量、常量、局部变量和参数集合赋值；无法静态确定时 MUST 标记具体属性为动态或无效，不得执行用户代码或猜测结果。
- **FR-004**: 配置静态死信交换机的队列 MUST 被识别为死信来源队列，无论其名称是否包含 `dead`、`dlq` 或其他命名标记。
- **FR-005**: 同时配置有效非负队列存活时间和死信交换机的队列 MUST 被识别为基于过期转发的延迟队列。
- **FR-006**: 仅配置队列存活时间的队列 MUST 展示存活时间，但不得展示不存在的死信目标；仅配置死信交换机的队列 MUST 展示死信关系，但不得展示不存在的固定延迟时长。
- **FR-007**: 系统 MUST 为特殊队列展示队列名称、队列类型、存活时间、死信交换机、死信路由方式及解析状态中所有已知信息。
- **FR-008**: 当死信路由键未配置时，系统 MUST 明确表示沿用消息原路由键，并依据原路由键是否可知决定关系是精确、候选还是无法确定。
- **FR-009**: 系统 MUST 将死信来源队列与当前项目中静态匹配的死信交换机、绑定和目标队列关联；存在多个匹配目标时 MUST 全部保留。
- **FR-010**: 当完整目标关系无法静态确定时，系统 MUST 保留已解析的源队列和死信参数，显示无法确定的原因，不得省略整个队列或虚构目标。
- **FR-011**: 特殊队列、死信交换机、绑定和目标队列的用户可见关系 MUST 支持跳转到各自真实源码声明位置；位置失效时沿用现有失效提示。
- **FR-012**: 特殊队列 MUST 保留现有模块归属、排序和去重规则；跨模块声明不得阻止关系匹配。
- **FR-013**: 现有文本搜索 MUST 能通过队列名、死信交换机、死信路由键和特殊队列类型定位相关节点，并继续与消息系统筛选共同生效。
- **FR-014**: 手动刷新 MUST 重新计算特殊队列属性和关系；刷新失败时 MUST 沿用现有旧树保留和失败提示规则。
- **FR-015**: 持久缓存 MUST 无损保存并恢复特殊队列类型、存活时间、死信参数、解析状态、关系所需数据和源码位置；旧格式无法表达这些数据时不得恢复为看似完整的新结果。
- **FR-016**: 系统 MUST 隔离单个无法解析的特殊队列声明，其他普通队列和特殊队列仍可继续展示。
- **FR-017**: 系统 MUST 防止死信关系环路导致无限展开、重复节点增长或界面无响应。
- **FR-018**: 本功能 MUST NOT 修改用户项目源码、配置或构建文件，MUST NOT 连接、查询或修改 RabbitMQ 运行时服务。
- **FR-019**: 本功能 MUST NOT 改变现有普通 RabbitMQ、Kafka 和 RocketMQ 端点的解析、匹配、刷新、缓存和导航行为。

### Scope Boundaries

**In Scope**:

- 当前项目源码中通过队列参数表达的 RabbitMQ 死信交换机、可选死信路由键和队列存活时间。
- 用户示例 `GenerateClearanceStatusMqConfiguration#broadcastWriteOffQueue` 所采用的参数集合声明形式。
- 等价的单参数声明形式，以及可静态追踪的字面量、常量、局部变量和参数集合赋值。
- 基于队列存活时间与死信转发组合形成的延迟队列。
- 源队列、死信交换机、绑定和目标队列之间的静态关系展示与源码导航。
- 现有侧边栏、刷新、缓存、搜索、筛选和模块分组对新增属性的完整支持。

**Out of Scope**:

- 基于 `x-delayed-message` 插件交换机、消息级 `x-delay` 头或其他 broker 插件实现的延迟消息。
- 消息级过期时间、重试次数、消费异常策略、重试队列编排或消息重放。
- RabbitMQ 管理接口、broker 运行时拓扑、队列深度、消息状态或实际投递结果。
- 根据队列或交换机名称中的 `dead`、`delay`、`retry` 等文本推断未声明的关系。
- 修改用户项目中的 RabbitMQ 配置，或自动生成缺失交换机、绑定和队列。
- 新增独立的死信管理页面、延迟消息发送入口或运行时运维功能。

### Key Entities *(include if feature involves data)*

- **特殊队列声明**: 当前项目中的 RabbitMQ 队列及其源码位置，包含普通队列、死信来源队列和基于过期转发的延迟队列分类。
- **队列转发属性**: 与队列关联的存活时间、死信交换机、死信路由方式和各属性解析状态；只有源码明确提供的信息才可作为确定值。
- **死信路径**: 从源队列经死信交换机和绑定到一个或多个目标队列的静态关系；关系可以是完整、候选或无法确定。
- **目标死信队列**: 通过当前项目中的交换机和绑定声明与死信路径匹配的队列，不依赖名称推断。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对参数集合和单参数两种声明形式各至少 10 个静态样例，死信交换机、死信路由方式和存活时间识别正确率为 100%。
- **SC-002**: 对完整单目标、完整多目标、缺失绑定、缺失目标队列和未指定死信路由键各至少 5 个样例，死信路径状态与实际源码一致率为 100%，虚构目标数量为 0。
- **SC-003**: 对“仅死信交换机”“仅存活时间”“存活时间加死信交换机”三类样例各至少 10 个，队列类型区分正确率为 100%。
- **SC-004**: 对动态交换机、动态路由键、动态存活时间、无效存活时间和分支修改参数集合各至少 5 个样例，保留可见队列并给出明确诊断的比例为 100%，错误确定值数量为 0。
- **SC-005**: 用户在包含至少 20 个特殊队列的多模块项目中，可在 30 秒内通过搜索或模块树定位任一指定特殊队列，并查看其已知延迟和死信路径信息。
- **SC-006**: 对每类特殊队列至少执行 10 次刷新和 10 次重新打开项目后的缓存恢复，属性、关系和源码位置与最新完整扫描结果一致率为 100%。
- **SC-007**: 现有 50 模块、2,000 个端点、40 次用户可见刷新性能回归继续满足 nearest-rank p95 严格小于 3 秒，环路样例的展示时间不随重复展开持续增长。
- **SC-008**: 完整验证期间，普通 RabbitMQ、Kafka 和 RocketMQ 既有样例结果变化数量为 0，用户项目非用户文件改动数量为 0，对 RabbitMQ 的连接尝试数量为 0。

## Assumptions

- 本功能中的“延迟队列”默认指用户示例采用的队列存活时间加死信转发模式，不包含 RabbitMQ 延迟消息插件模式。
- 死信目标通过交换机、路由方式和现有绑定确定，不通过队列、方法或常量名称猜测。
- 未配置专用死信路由键时，消息沿用原路由键；只有原路由信息和交换机类型足以判断时才形成精确目标。
- 有效队列存活时间为可静态确定的非负时长；`0` 是可展示的明确值，不等同于缺失。
- 参数集合中的其他队列属性不属于本次展示范围，但不得阻止死信和存活时间属性识别。
- 特殊队列关系是现有 RabbitMQ 拓扑数据的增量信息，继续服从当前项目范围、只读分析、动态降级和源码导航规则。
- 若现有持久缓存格式不能完整表达新增属性，后续 planning 需要定义明确的缓存版本迁移或失效策略。
