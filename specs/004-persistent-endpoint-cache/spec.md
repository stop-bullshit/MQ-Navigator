# Feature Specification: MQ 端点持久缓存

**Feature Branch**: `[004-persistent-endpoint-cache]`

**Created**: 2026-08-24

**Status**: Draft

**Input**: User description: "参考 InterfaceX 实现缓存功能，然后全部自己分析修改实现"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 重新打开项目时快速恢复端点 (Priority: P1)

开发人员曾在当前项目完成过一次 MQ 端点扫描。关闭并重新打开 IDE 或项目后，再次打开 MQ Navigator 时，应优先恢复上次成功扫描的端点，不必等待完整项目扫描后才能浏览树、搜索端点或查看模块分组。

**Why this priority**: 大型项目首次扫描耗时最明显，快速恢复上次结果是缓存功能的主要用户价值。

**Independent Test**: 在包含 2,000 个端点的只读项目中先生成缓存，再创建新的项目服务实例并打开端点列表；可独立验证恢复速度、端点完整性和源码导航，无需执行手动刷新。

**Acceptance Scenarios**:

1. **Given** 当前项目存在上次成功扫描的有效缓存，**When** 项目服务首次读取端点，**Then** 系统返回缓存中的完整端点列表，且不先执行完整项目扫描。
2. **Given** 上次成功扫描结果合法且为空，**When** 项目重新打开，**Then** 系统恢复合法空结果，不展示更早的过期端点。
3. **Given** 缓存恢复了端点，**When** 用户搜索、筛选、展开模块或双击端点，**Then** 展示和源码定位继续使用现有规则。

---

### User Story 2 - 刷新后更新缓存 (Priority: P1)

开发人员修改 MQ 配置或代码后，可以使用现有刷新入口获取最新结果。刷新必须绕过旧缓存，扫描当前源码，并在结果可用后替换缓存；之后重新打开项目应恢复这次新结果。

**Why this priority**: 缓存必须与现有刷新入口协同，否则用户可能长期看到过期端点。

**Independent Test**: 先缓存一个目的地，修改只读测试项目中的端点声明并触发刷新，验证当前结果和下一次服务恢复结果都变为新目的地；不依赖工具窗口人工操作。

**Acceptance Scenarios**:

1. **Given** 当前项目已恢复旧缓存，**When** 用户触发现有刷新入口，**Then** 系统跳过旧缓存并扫描当前项目，展示最新结果。
2. **Given** 新扫描成功，**When** 项目服务再次启动，**Then** 恢复的是新扫描结果，不是被替换的旧缓存。
3. **Given** 项目在当前会话中发生源码或项目结构变化，**When** 下一次读取端点，**Then** 系统重新计算结果并更新缓存。
4. **Given** 新扫描未能形成可用的完整快照，**When** 扫描结束，**Then** 系统不得用不完整结果覆盖上次成功缓存。

---

### User Story 3 - 无效缓存安全降级 (Priority: P2)

开发人员使用不同项目、移动或删除源码文件，或者遇到旧版本及损坏缓存时，MQ Navigator 应自动放弃整份无效缓存并按现有方式扫描项目，不能崩溃、展示跨项目数据或使用部分过期结果。

**Why this priority**: 持久缓存跨越项目生命周期，必须确保错误隔离和项目边界正确。

**Independent Test**: 分别提供版本不匹配、字段损坏、源码位置失效和其他项目的缓存，验证每种情况都回退扫描并生成当前项目的新缓存。

**Acceptance Scenarios**:

1. **Given** 缓存版本不受支持或内容损坏，**When** 系统首次读取端点，**Then** 系统忽略整份缓存、完成当前项目扫描并修复缓存。
2. **Given** 缓存中任一源码位置已无法还原，**When** 系统恢复缓存，**Then** 系统不展示部分缓存，而是回退完整扫描。
3. **Given** 同时打开两个项目，**When** 两个项目分别读取或刷新端点，**Then** 各自只能访问本项目缓存和源码。
4. **Given** 缓存不可用，**When** 系统回退扫描，**Then** 现有等待索引、刷新进度、失败反馈和旧树保留规则不变。

### Edge Cases

- 项目从未完成过成功扫描，没有任何缓存。
- 上次成功扫描结果为空，必须与“缓存缺失”区分。
- 缓存版本不匹配、必要字段缺失、枚举值无法识别或条目重复。
- 缓存引用的源码文件已删除、移动，或保存位置已超出文件范围。
- 缓存条目可以还原一部分但不能全部还原，必须整批回退而非展示部分结果。
- 手动刷新发生在缓存刚恢复之后，旧缓存不得阻止新扫描。
- 当前会话中的源码或项目根变化使已恢复快照失效。
- 多个项目名称相同但路径不同，缓存仍不得串用。
- 缓存写入不可用时，当前扫描结果仍应可使用，且不得修改用户项目。
- 动态端点、合法空目的地字段、多 binding key 和同源多目的地端点必须无损恢复。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每个项目保留最近一次成功形成的完整 MQ 端点快照，范围包含 RabbitMQ、Kafka 和 RocketMQ 的现有已支持端点。
- **FR-002**: 缓存 MUST 按项目隔离；同名项目、并行打开项目和不同项目路径之间不得共享端点结果。
- **FR-003**: 缓存数据 MUST 存放在用户项目之外，不得创建或修改项目源码、配置、构建文件及项目级缓存文件。
- **FR-004**: 项目服务启动后的首次端点读取 MUST 优先尝试恢复有效缓存；有效缓存恢复成功时不得先执行完整项目扫描。
- **FR-005**: 系统 MUST 区分“没有缓存”和“上次成功结果为空”，合法空缓存不得恢复更早的非空结果。
- **FR-006**: 缓存 MUST 保留端点展示、匹配和源码定位所需的全部现有业务字段，包括系统类型、角色、目的地、解析状态、模块、文件、类、成员和源码位置。
- **FR-007**: 缓存恢复 MUST 验证版本、必要字段和全部源码位置；任一端点无法完整还原时 MUST 放弃整份缓存并回退扫描。
- **FR-008**: 从缓存恢复的端点 MUST 保持现有排序、去重、不可修改快照、动态提示、匹配和源码导航行为。
- **FR-009**: 用户通过现有刷新入口刷新时，系统 MUST 绕过持久缓存并扫描当前项目。
- **FR-010**: 当前会话中的源码或项目根变化使现有快照失效后，下一次端点读取 MUST 重新扫描并更新缓存。
- **FR-011**: 每次成功形成完整扫描快照后，系统 MUST 用该快照替换本项目旧缓存，包括合法空结果。
- **FR-012**: 未能形成完整扫描快照时，系统 MUST 保留上次成功缓存，不得写入部分结果或损坏状态。
- **FR-013**: 缓存缺失、版本不匹配、内容损坏或源码位置失效时，系统 MUST 自动回退现有扫描流程，并在成功后生成新缓存。
- **FR-014**: 缓存恢复和回退扫描 MUST 继续遵守现有索引等待、后台读取、项目关闭和最新刷新结果规则。
- **FR-015**: 缓存功能 MUST NOT 连接、查询或修改 RabbitMQ、Kafka、RocketMQ 及其他运行时消息服务。
- **FR-016**: 缓存功能 MUST NOT 改变现有刷新入口、模块折叠、搜索、类型筛选、数量、动态提示、匹配结果和双击导航规则。
- **FR-017**: 缓存格式变化 MUST 通过明确版本识别；不受支持的旧缓存不得被近似解释。

### Scope Boundaries

**In Scope**:

- 当前项目全部已支持 MQ 端点的最近一次成功快照。
- 项目重新打开后的缓存恢复、手动刷新绕过、会话内失效和成功扫描后的替换。
- 缓存条目到真实当前项目源码位置的恢复。
- 缓存缺失、损坏、版本不匹配和源码失效时的完整扫描降级。
- 项目隔离、用户项目只读、broker 零连接和现有性能门槛验证。

**Out of Scope**:

- 新增缓存管理、清空缓存、过期时间或自动刷新设置界面。
- 多历史版本、增量条目合并、跨项目共享、云同步或团队共享缓存。
- 自定义数据库、外部缓存服务、消息系统运行时拓扑缓存。
- 新增文件监听器、定时刷新、轮询、重试、后台线程池或锁。
- 修改 parser、matcher、目的地识别规则、刷新按钮和消息系统支持范围。

### Key Entities *(include if feature involves data)*

- **项目端点缓存快照**: 当前项目最近一次成功形成的完整端点集合，包含格式版本、保存时间和零个或多个缓存条目；合法空集合也是有效快照。
- **缓存端点条目**: 一个端点的系统、角色、目的地、解析状态、展示身份和源码位置数据；只有全部字段与源码位置可还原时才有效。
- **缓存源码位置**: 指向当前项目源码文件和文件内位置的稳定描述，用于恢复真实源码导航目标，不保存运行中的源码对象。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 5 次预热后，对包含 2,000 个端点的有效缓存执行至少 20 次全量恢复，用户可读取完整端点列表的 nearest-rank p95 不超过 500 毫秒。
- **SC-002**: 对 RabbitMQ、Kafka、RocketMQ 的生产者、消费者及现有拓扑角色各至少 5 个样例，缓存恢复前后全部业务字段和源码导航目标一致率为 100%。
- **SC-003**: 对成功刷新、合法空刷新和会话内源码变化各至少 5 次，下一次服务启动恢复最新结果的正确率为 100%，旧结果残留次数为 0。
- **SC-004**: 对版本不匹配、必要字段损坏、源码文件删除、源码位置越界和跨项目缓存各至少 5 次，自动回退完整扫描的成功率为 100%，部分缓存展示次数为 0，未处理异常次数为 0。
- **SC-005**: 现有 50 模块、2,000 endpoint、40 次用户可见刷新性能回归继续满足 nearest-rank p95 严格小于 3 秒。
- **SC-006**: 完整测试、缓存恢复、回退和刷新验证期间，用户项目非用户文件改动数量为 0，对 RabbitMQ、Kafka、RocketMQ 的连接尝试均为 0。
- **SC-007**: 两个并行项目各执行至少 10 次缓存恢复和刷新后，跨项目端点泄漏次数为 0。

## Assumptions

- 缓存是现有项目端点快照的持久化种子，不形成独立的第二套运行时真相来源。
- 缓存没有时间过期策略；用户手动刷新和当前会话中的源码或项目根变化负责更新结果。
- 只有最近一次完整成功快照被保留，不保存历史快照或部分 parser 结果。
- 缓存恢复采用整批有效原则；任一条目无法还原时，完整扫描比展示部分旧结果更可靠。
- 缓存保存位置由 IDE 提供并位于用户项目之外，项目卸载或缓存清理后允许自然丢失。
- 现有刷新进度、错误反馈和旧树保留行为继续作为用户可见状态来源，不新增缓存管理入口。
- `D:\github\interfacex` 仅作为“缓存优先、手动刷新更新缓存、缓存导航恢复”的只读行为参考，不复制其数据库、线程和 UI 结构。
