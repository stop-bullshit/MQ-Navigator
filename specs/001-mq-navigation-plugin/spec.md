**Feature Branch**: 未创建（未配置 `before_specify` 分支钩子）

**Created**: 2026-08-17

**Status**: Ready for Planning

**Input**: User description: "这是一个 IDEA 插件，可以扫描项目代码并在 FeignClient 调用方和 Server 端之间跳转。参考这个项目，新建一个可以在消息队列发送端和接收端之间跳转的插件，并在 D:\github 目录下新建项目实现。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从发送端定位接收端 (Priority: P1)

开发人员阅读消息发送代码时，可以从发送位置直接查看并跳转到当前项目中消费该消息的接收位置，从而快速理解消息去向，无需全局搜索消息目的地名称。

**Why this priority**: 发送端到接收端是最核心、最常用的排查路径，单独交付即可形成可用的最小版本。

**Independent Test**: 在包含一个可静态识别发送端和一个匹配接收端的示例项目中，从发送位置触发导航，应直接打开对应接收位置。

**Acceptance Scenarios**:

1. **Given** 当前项目中存在一个发送端和唯一匹配的接收端，**When** 用户在发送位置触发导航，**Then** 编辑器直接打开并定位到该接收位置。
2. **Given** 发送端使用字符串字面量、编译期常量，或直接引用一个由项目配置占位符赋值且可唯一确定的字段声明消息目的地，**When** 用户触发导航，**Then** 系统按确定后的目的地信息找到匹配接收端。
3. **Given** 当前项目中不存在匹配接收端，**When** 用户在发送位置触发导航，**Then** 系统明确提示未找到接收端且不跳转到无关代码。

---

### User Story 2 - 从接收端反查发送端 (Priority: P2)

开发人员阅读消息接收代码时，可以反向查看并跳转到可能向该目的地发送消息的位置，以便追踪消息来源和影响范围。

**Why this priority**: 反向追踪补齐完整的双向导航能力，但发送到接收的主路径不依赖该能力即可使用。

**Independent Test**: 在包含一个接收端和一个匹配发送端的示例项目中，从接收位置触发导航，应直接打开对应发送位置。

**Acceptance Scenarios**:

1. **Given** 当前项目中存在一个接收端和唯一匹配的发送端，**When** 用户在接收位置触发导航，**Then** 编辑器直接打开并定位到该发送位置。
2. **Given** 当前项目中不存在匹配发送端，**When** 用户在接收位置触发导航，**Then** 系统明确提示未找到发送端且保留用户当前编辑位置。
3. **Given** RabbitMQ 消息由外部系统发送且项目使用 `QueueBuilder.durable(CONSTANT)` 声明队列，**When** 用户在 listener 或队列声明位置触发导航，**Then** 两者可按静态队列名双向跳转，且项目内发送端存在时仍优先发送端与 listener 的直接关系。

---

### User Story 3 - 在多个候选位置中选择 (Priority: P2)

当同一消息存在多个接收端或多个发送端时，开发人员可以先查看带有项目上下文的候选列表，再选择目标位置，避免插件擅自跳转到错误位置。

**Why this priority**: 广播消费、多个消费组和多个发送入口都很常见；没有歧义选择会直接降低导航可信度。

**Independent Test**: 构造一个发送端对应多个接收端、一个接收端对应多个发送端的项目，分别触发双向导航，应显示完整候选并跳转到用户选择的位置。

**Acceptance Scenarios**:

1. **Given** 一个发送端匹配多个接收端，**When** 用户触发导航，**Then** 系统展示全部有效接收候选及其模块、文件和代码位置，用户选择后才执行跳转。
2. **Given** 一个接收端匹配多个发送端，**When** 用户触发导航，**Then** 系统展示全部有效发送候选且不默认隐藏任何同等有效的候选。
3. **Given** 候选列表中某个代码位置已被删除或失效，**When** 用户打开候选列表，**Then** 失效位置不会作为可跳转目标出现。

---

### User Story 4 - 获得最新且可信的导航结果 (Priority: P3)

开发人员新增、修改、重命名或删除消息端点后，无需重启 IDE 即可获得与当前源码一致的导航结果；必要时也可以主动重新扫描。

**Why this priority**: 最新结果决定长期使用体验，但在首轮静态扫描结果可用时，核心导航流程已经能够独立提供价值。

**Independent Test**: 在导航入口已经显示的项目中依次新增、修改和删除端点，不关闭或重新打开源文件，直接再次触发同一入口并验证候选更新；随后主动重新扫描，结果仍与当前源码一致。

**Acceptance Scenarios**:

1. **Given** 用户修改了可静态解析的消息目的地且修改前的导航入口仍显示在编辑器中，**When** 修改完成、项目可分析且用户再次触发该入口，**Then** 本次导航使用当前项目状态，不再返回旧匹配。
2. **Given** 自动更新尚未完成或用户怀疑结果过期，**When** 用户主动重新扫描，**Then** 扫描完成后导航结果与当前项目源码一致。
3. **Given** 项目中存在语法不完整的正在编辑文件，**When** 系统更新导航结果，**Then** 其他可识别端点仍可正常导航，问题文件不会导致整个项目导航不可用。

### Edge Cases

- 相同目的地名称出现在不同消息系统中时，只能在同一消息系统及相容目的地信息内匹配，不能跨系统误关联。
- 同一项目的多个模块声明相同目的地且存在多个有效端点时，必须全部作为候选展示，并提供足以区分它们的源码上下文。
- 目的地由运行时数据、复杂表达式或外部配置动态生成且无法从当前项目确定时，必须标记为无法静态定位，不能猜测目标。
- 目的地通过字符串字面量、Java 编译期常量引用或可读取配置间接声明时，应在值可唯一确定的情况下参与匹配。
- 发送端直接引用由配置占位符赋值的字段时，只有字段值在所属模块内可唯一确定才参与精确匹配；不同配置文件给出不同值时必须提示歧义。
- 枚举常量的无参字符串 getter 只有在源码中可把 getter 字段明确映射到该枚举常量的构造参数时才参与匹配；其他 getter、构造参数流、方法返回或跨方法传递仍视为无法静态确定。
- 接收端带有额外筛选条件时，匹配必须保留这些条件；不能仅因基础目的地相同就将明显不相容的端点判为精确匹配。
- 代码重命名、移动或删除后，旧位置不得继续作为可跳转候选。
- 发送端或接收端位于外部依赖、未打开的仓库或仅有编译产物时，首版不提供跨项目跳转，并应将结果视为当前项目内未找到。
- 某个端点在运行时是否启用由部署配置决定；插件只表达源码中的可能关系，不声称消息在运行时一定可达。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须扫描当前打开项目的源码模块，并识别首版支持范围内的消息发送端和消息接收端。
- **FR-002**: 首版必须覆盖 Java/Spring 项目中常见的 RabbitMQ、Kafka 和 RocketMQ 静态发送、接收声明，以及 RabbitMQ `QueueBuilder.durable(...)` 队列与 `BindingBuilder`/`ExchangeBuilder` 静态拓扑；每类支持方式必须纳入可重复执行的兼容性样例。
- **FR-003**: 系统必须为每个已识别端点生成消息系统类型、端点角色（发送、接收或队列声明）、消息目的地信息及源码位置，且只有静态可确定的信息才能用于精确匹配。
- **FR-004**: 系统必须按照消息系统各自要求的完整目的地和筛选信息关联发送端与接收端，不能只比较单个同名字符串。
- **FR-005**: 已识别的发送端和接收端必须在编辑器中提供可发现的导航入口，并能明确区分“跳转到接收端”和“跳转到发送端”。
- **FR-006**: 当且仅当存在一个有效目标时，用户触发导航后必须直接定位到该目标源码位置。
- **FR-007**: 当存在多个有效目标时，系统必须先展示全部候选；每个候选至少包含模块、文件、所属代码位置和消息目的地摘要，用户选择后才执行跳转。
- **FR-008**: 当不存在有效目标时，系统必须给出方向明确的未匹配提示，不得跳转到近似或无关代码。
- **FR-009**: 系统必须同时支持“发送端到接收端”和“接收端到发送端”的一对一、一对多及多对一关系。
- **FR-010**: 系统必须使用字符串字面量、Java 编译期常量引用，以及源码可证明的枚举常量无参字符串 getter 参与匹配；对于发送端，首版还必须支持直接引用由单一配置占位符赋值且在所属模块可唯一确定的字段；对于接收端，首版必须支持可唯一确定的配置引用。局部变量别名、普通对象 getter、构造参数流、方法返回、跨方法传递、复杂表达式或多值配置必须提示无法静态定位并停止精确匹配。
- **FR-011**: 当端点源码或其参与匹配的配置新增、修改、移动、重命名或删除后，系统必须在无需重启 IDE 的情况下更新后续导航结果；即使导航入口在变更前已经显示，用户下一次触发时也必须基于当前可分析的项目状态，并且系统必须提供用户可主动触发的重新扫描能力。
- **FR-012**: 单个文件无法分析时，系统必须隔离该文件的失败，不得使其他已识别端点的导航整体失效。
- **FR-013**: 扫描和导航过程不得修改用户项目源码、配置或构建文件，也不得连接消息服务或发送、消费任何真实消息。
- **FR-014**: 导航候选必须限定在当前打开项目可读取的源码范围内；外部依赖、远程仓库和运行时实例发现不属于首版能力。
- **FR-015**: RabbitMQ 工具窗口必须先按模块、再按 Consumers、Producers 和 Topology 分类展示端点，支持文本和端点类型筛选，并允许从关联 binding、consumer 或 producer 节点打开源码。

### Scope Boundaries

**In Scope**:

- 当前打开 IDEA 项目内、跨源码模块的消息发送端与接收端扫描。
- RabbitMQ、Kafka、RocketMQ 的常见静态声明、项目内编译期常量、可证明的枚举常量字符串 getter、接收端配置引用，以及发送端直接引用的单一配置占位符字段。
- RabbitMQ `QueueBuilder.durable(...)` 的静态队列声明、`BindingBuilder`/`ExchangeBuilder` 拓扑解析，以及从队列/监听器通过交换机反查发送端。
- 编辑器内双向导航、单目标直达、多目标选择、未匹配反馈和主动重新扫描。
- RabbitMQ 项目级工具窗口、模块/收发端分组、关系展示和筛选。
- 源码变更后的结果更新，以及无法静态确定目标时的安全降级。

**Out of Scope**:

- 连接消息服务查询运行时拓扑、积压、消费状态或消息轨迹。
- 发送、接收、重放或修改真实消息。
- 跳转到未打开仓库、外部依赖或仅有编译产物中的端点。
- 执行任意业务代码、脚本或动态表达式以推算运行时目的地。
- 沿局部变量别名、普通对象 getter、构造参数、方法返回或跨方法调用链推导发送端配置值。
- 判断某个端点在具体部署环境中是否实际启用或可达。
- 自动修改用户源码、配置或构建文件。

### Key Entities

- **消息端点**: 项目源码中的一个发送、接收或静态队列声明位置；包含端点角色、消息系统类型、源码位置和可解析的目的地信息。
- **消息目的地标识**: 用于判断端点是否可能通信的一组信息；包含消息系统类型、基础目的地以及该消息系统要求的路由或筛选条件。
- **导航匹配**: 一个源端点与一个或多个有效目标端点之间的静态关联；包含匹配方向、匹配状态和候选集合。
- **项目扫描结果**: 当前项目在某一源码状态下识别出的端点及其关联，用于判断结果是否需要更新。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在覆盖三类支持消息系统及其已声明兼容方式的标准样例集中，100% 的静态发送端和接收端都能显示正确方向的导航入口。
- **SC-002**: 在标准样例集中，所有唯一匹配均跳转到正确源码位置，跨消息系统或目的地不相容导致的错误跳转数量为 0。
- **SC-003**: 在包含 50 个实际可独立识别源码模块和 2,000 个消息端点的验收项目中，初次扫描完成后，95% 的导航操作在 1 秒内得到完整、已过滤且顺序稳定的目标或候选结果；界面绘制时间不纳入此项自动化性能门槛，用户完成导航的体验由 SC-004 验证。不得使用单一模块内的逻辑分组替代 50 个实际模块。
- **SC-004**: 至少 90% 的试用开发人员无需查阅说明，即可在首次尝试的 5 秒内从一个已识别端点完成双向导航任务。
- **SC-005**: 对新增、修改、移动和删除端点或其参与匹配配置的验收操作，内容已提交且项目可分析后，95% 的后续导航操作在 3 秒内得到最新目标或候选结果；点击变更前已显示的导航入口不得返回旧匹配，主动重新扫描后 100% 与当前项目内容一致。
- **SC-006**: 完整验收必须以前后一致范围的文件基线进行比较；用户项目源码、配置和构建文件的非用户改动数量为 0，对真实消息服务的连接次数为 0。

## Assumptions

- 新项目目录采用 `D:\github\mqx-plugin`，插件暂用产品名“MQ Navigator”；名称可在规划阶段调整，不改变本规格的功能范围。
- 目标用户是在 IDEA 中维护 Java/Spring 多模块项目、需要追踪异步消息调用关系的开发人员。
- 首版优先处理源码中可静态确定的消息关系；运行时才能确定的关系允许明确降级为“无法静态定位”。
- 首版对发送端配置的静态分析仅覆盖直接字段引用，且该字段由单一配置占位符赋值；其他依赖注入或数据流形式不在首版范围。
- 性能验收项目提供 50 个实际源码模块和合计 2,000 个端点，并允许以相同环境重复采样导航与刷新耗时。
- SC-004 使用至少 10 名首次使用 MQ Navigator 的目标开发人员，在同一验收项目、同一起始文件和导航入口已显示的条件下测试；从发出任务指令开始计时，完成发送端到接收端并反向返回发送端时停止，过程中不得查阅说明，至少 9 人需在 5 秒内完成。
- 用户需要同时打开包含相关发送端和接收端源码的项目；插件不负责拉取其他仓库或反编译外部依赖。
- 静态导航表示源码层面的可能通信关系，不等同于运行时消息送达证明。
- 用户可接受与参考插件一致的基本交互：在代码位置发现导航入口，唯一目标直接跳转，多个目标先选择，无目标时获得明确反馈。
- 后续规划必须优先复用参考项目已经验证的扫描、导航和源码变更感知思路，同时保持新项目独立，不直接修改或依赖参考项目工作区中的未提交源码。
